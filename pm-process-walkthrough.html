The Framework: Double Diamond + Lean Startup

This walkthrough combines the Double Diamond (discover → define → develop → deliver) with Lean Startup (build → measure → learn). This hybrid is the most popular approach at top tech companies because it balances user empathy with speed of execution.

1

Discover & Research

Understand the problem space before jumping to solutions

2-4 weeks

The biggest mistake PMs make is skipping this phase. Every failed product can be traced back to insufficient understanding of the problem, the user, or the market.

What You Do

  • User research: Conduct 10-15 user interviews. Use open-ended questions. Record and transcribe. Look for patterns in pain points, not feature requests.
  • Market analysis: Size the market (TAM/SAM/SOM). Identify trends. Understand the competitive landscape — who else is solving this problem and how?
  • Data mining: If you have an existing product, analyze usage data. Where do users drop off? What features are underused? What do support tickets say?
  • Stakeholder interviews: Talk to sales, support, and leadership. What are they hearing from customers? What does the business need?
  • Competitive teardowns: Use the top 3-5 competitors' products. Document strengths, weaknesses, and gaps.
Pro Tip

Use The Mom Test approach: don't ask "Would you use this?" (they'll say yes to be nice). Ask about their current behavior: "How do you solve this problem today? What's the most annoying part? How much time/money does it cost you?"

Key Deliverables

  • User research synthesis (key themes and quotes)
  • User personas (2-3 primary personas based on real data)
  • Market sizing document (TAM, SAM, SOM)
  • Competitive landscape map
  • Problem hypothesis to validate
2

Define the Problem

Narrow from broad research to a specific, solvable problem

1-2 weeks

You've done your research. Now synthesize it into a crystal-clear problem statement. A well-defined problem is half the solution.

What You Do

  • Synthesize research: Cluster findings into themes. Use affinity mapping to find the top 3-5 pain points.
  • Write a problem statement: "[User persona] struggles with [specific problem] when trying to [goal], which results in [negative outcome]."
  • Apply Jobs to Be Done: Frame it as a job: "When [situation], I want to [motivation], so I can [expected outcome]."
  • Define success: What does solving this problem look like? What metric moves? For whom? By how much?
  • Align stakeholders: Get buy-in on the problem before discussing solutions. This prevents endless solution debates later.
Framework: Jobs to Be Done

People don't buy products — they hire them to do a job. Understanding the job unlocks the right solution.

Example: "When I'm commuting home and want to cook dinner, I want to quickly find a recipe using ingredients I already have, so I can avoid an extra grocery trip and still eat well."

Common Mistake

Defining the problem as "users need [your solution]." That's a solution disguised as a problem. The problem should be describable without mentioning your product. "Users waste 30 minutes per day context-switching between 5 communication tools" is a problem. "Users need a unified inbox" is a solution.

Key Deliverables

  • Problem statement (1-2 sentences)
  • JTBD statements for primary personas
  • Success criteria and target metrics
  • Stakeholder alignment (documented agreement on the problem)
3

Ideate Solutions

Generate many possible solutions before committing to one

1-2 weeks

Now that the problem is clear, brainstorm widely before narrowing. The goal is to explore the solution space, not to commit to the first idea.

What You Do

  • Divergent brainstorming: Generate 10-20 solution ideas. Include wild ideas. No filtering yet. Involve design, engineering, and other perspectives.
  • Design sprint (optional): Use Jake Knapp's Sprint method for a structured 5-day ideation process with the team.
  • Competitive inspiration: How do adjacent products solve similar problems? Don't copy, but learn from patterns.
  • Evaluate solutions: Use a Value vs Complexity matrix. Plot all ideas. Discuss as a team.
  • Select top 2-3: Pick the most promising ideas to prototype and test. Don't commit to one yet.
Pro Tip: "How Might We" Questions

Reframe problems as "How Might We" (HMW) questions to unlock creative solutions. "Users waste time switching between tools" becomes "How might we give users a unified view of all their communications?" Each HMW question opens a different solution direction.

Amazon's Working Backwards Method

Before building anything, write the press release for the finished product. This forces clarity on:

  1. Who is the customer? Be specific.
  2. What is the customer problem? In their words.
  3. What is the solution? How does it work?
  4. Why should the customer care? What's the benefit?
  5. How does the customer get started? What's the first experience?

If you can't write a compelling press release, the idea isn't clear enough yet.

Key Deliverables

  • Solution brainstorm document (10-20 ideas)
  • Value vs Complexity matrix
  • Top 2-3 solutions selected for validation
  • Internal press release (Working Backwards)
4

Validate & Prototype

Test your assumptions before committing engineering resources

2-3 weeks

This is where most PMs skip ahead to "let's just build it" — and waste months on the wrong thing. Validation is the highest-ROI activity in product management.

What You Do

  • Identify riskiest assumption: What must be true for this to work? That's what you test first. Not the whole product — the riskiest assumption.
  • Build prototypes: Low-fidelity first (paper sketches, Figma clickthrough). Only go high-fidelity if needed for user testing.
  • User testing: Put the prototype in front of 5-8 target users. Watch them use it. Don't explain — observe. After 5 users, you'll see 85% of usability issues.
  • Wizard of Oz test: For complex features, simulate the experience manually before building it. (Example: Zappos founder tested demand by posting shoe photos online, then buying from stores and shipping manually.)
  • Fake door test: Add a button or CTA for the feature. Measure how many users click. If nobody clicks, nobody wants it.
  • Iterate: Prototype → test → learn → revise → test again. 2-3 rounds is typical.
Real-World Example: Dropbox

Drew Houston didn't build Dropbox first. He made a 3-minute video showing what the product WOULD do. The waitlist went from 5,000 to 75,000 overnight. He validated demand before writing a single line of code. That's the gold standard of validation.

Framework: The Riskiest Assumption Test (RAT)

List your assumptions. Rank by risk (impact if wrong × likelihood of being wrong). Test the top one first.

  1. List all assumptions: "Users will pay for this." "Users understand the value proposition." "We can build this in 6 weeks."
  2. Rank by risk: Which assumption, if wrong, kills the project?
  3. Design the cheapest, fastest test for that assumption
  4. Set a pass/fail threshold BEFORE testing
  5. Test, learn, decide: proceed, pivot, or kill

Key Deliverables

  • Prototype (Figma, paper, or coded MVP)
  • User testing report (5-8 users, key findings)
  • Validated or invalidated assumptions
  • Go/no-go decision on proceeding to build
5

Plan & Prioritize

Define what to build, in what order, and how to measure success

1-2 weeks

You've validated the idea. Now turn it into a buildable plan. This is where the PRD, roadmap, and sprint planning happen.

Write the PRD

The Product Requirements Document is the PM's primary artifact. Keep it concise (2-4 pages) and living (update as you learn).

  1. Problem statement — What problem are we solving and for whom?
  2. Goals & success metrics — What does success look like? OKRs or specific KPIs.
  3. User stories — "As a [user], I want [action] so that [benefit]"
  4. Requirements — Functional (what it does) and non-functional (performance, security, accessibility)
  5. Designs — Link to Figma mockups or wireframes
  6. Out of scope — Explicitly state what you're NOT building
  7. Open questions — Unknowns to resolve during build
  8. Timeline — Milestones, not precise dates

Prioritize with RICE

Framework: RICE Scoring

Score = (Reach × Impact × Confidence) / Effort

I
Impact
C
Confidence
E

Reach: How many users per quarter? Use real numbers.
Impact: How much does it move the metric? (3=massive, 2=high, 1=medium, 0.5=low)
Confidence: How sure are you? (100%=data-backed, 80%=reasonable, 50%=guess)
Effort: Person-months of work across all roles.

Define the MVP

The Minimum Viable Product is the smallest version that delivers the core value. Use MoSCoW to scope:

  • Must-have: Without these, the product doesn't solve the core problem
  • Should-have: Important but the product works without them
  • Could-have: Nice to have — v2 candidates
  • Won't-have: Explicitly out of scope for this release

Key Deliverables

  • PRD reviewed and approved by stakeholders
  • RICE-scored backlog
  • MVP scope defined (MoSCoW)
  • Engineering estimates and sprint plan
  • OKRs for the initiative
6

Build & Iterate

Execute the plan with your engineering and design team

4-12 weeks

Building is where the PM shifts from "architect" to "air traffic controller." Your job is to keep the team unblocked, scope tight, and quality high.

Your Daily Responsibilities During Build

  • Attend standup: Listen for blockers. If an engineer is stuck on a requirement ambiguity, resolve it within hours, not days.
  • Scope management: Features ALWAYS try to grow. Your job is to protect the MVP scope. Every addition must justify itself against the timeline.
  • Design review: Review designs before they go to engineering. Catch issues early when they're cheap to fix.
  • QA partnership: Write acceptance criteria that QA can test. Review edge cases together. Don't just throw specs over the wall.
  • Stakeholder updates: Weekly status to leadership. Surface risks early. No surprises.
  • Dog-fooding: Use the product daily as it's being built. You should be the first user to find bugs.
Common Trap: Scope Creep

A stakeholder says: "While you're building this, can we also add [feature]?" Your answer: "Great idea. Let me add it to the backlog for v2. For this release, we're focused on [MVP goal] to ship by [date]." Write it down, acknowledge it, defer it. Scope creep is the #1 killer of product timelines.

Launch

Ship the product to real users with a plan for every scenario

1-2 weeks

Launch is not just "deploy the code." It's a cross-functional event involving engineering, marketing, sales, support, and legal. The PM orchestrates all of it.

Pre-Launch Checklist

  • All critical bugs resolved; known issues documented
  • Performance testing passed (load test at 2x expected traffic)
  • Security review completed
  • Legal/compliance sign-off (if applicable)
  • Support documentation written and CS team briefed
  • Marketing materials ready (blog post, social, email)
  • Sales enablement materials distributed
  • Analytics instrumented (events, funnels, dashboards)
  • Rollback plan tested and documented
  • On-call schedule established for launch week

Phased Rollout Strategy

Never launch to 100% on day one. Use feature flags for a gradual rollout:

  1. Internal dogfood (1-2 days): Your team uses it. Catch obvious issues.
  2. Beta users 5% (3-5 days): Opt-in beta group. Monitor error rates, support tickets, user feedback.
  3. Expand to 25% (3-5 days): Check metrics against targets. Resolve any issues.
  4. Go to 50% (2-3 days): Performance at scale. A/B test if applicable.
  5. Full 100% launch: Marketing announcement. All hands on deck for support.
Launch Day Checklist
  • Dashboard open and monitored continuously
  • Dedicated Slack channel for launch issues
  • Engineering on standby for hotfixes
  • Support team actively monitoring tickets
  • PM personally using the feature in production
  • Rollback criteria defined: "If error rate exceeds X%, roll back immediately"

Key Deliverables

  • Launch announcement (internal + external)
  • Completed rollout to 100%
  • Launch metrics snapshot (day 1, day 3, day 7)
  • Issues log with resolution status
8

Measure & Iterate

The product is live — now learn from real data and improve

Ongoing

Launching is not the end — it's the beginning of learning. The best PMs are obsessive about post-launch data because that's when you discover what actually works.

Post-Launch Activities

  • Monitor metrics daily (first 2 weeks): Track your North Star metric, funnel metrics, and guardrail metrics. Compare to pre-launch baseline.
  • Analyze user behavior: Are users using the feature as expected? Where do they drop off? What's surprising?
  • Collect qualitative feedback: Support tickets, app store reviews, social media mentions, user interviews. Numbers tell you WHAT, users tell you WHY.
  • Run retrospective: What went well? What didn't? What would you do differently? Document for the next launch.
  • Plan v2: Based on data and feedback, prioritize improvements. The first version is never perfect — that's by design.
Framework: Build → Measure → Learn (Lean Startup)

This is the cycle that never stops. Every launch feeds back into the next iteration.

Key Metrics to Review

  • Adoption: What % of eligible users are using the feature? Is it growing?
  • Engagement: How often do they use it? How deeply?
  • Retention: Do users come back after first use? D1, D7, D30 retention.
  • Task success: Can users complete the core task? What's the error/abandonment rate?
  • Satisfaction: NPS, CSAT, app store rating changes.
  • Business impact: Revenue, conversion, cost savings — whatever the original OKR targeted.
The Best PMs Do This

Write a "launch learnings" doc after every major launch. Include: what you hypothesized vs what actually happened, surprises, and what you'd change. Share it with the team. This compounds — after 10 launches, you have a playbook that makes you dramatically faster and more accurate.

Kill Criteria

Not everything should be iterated on. Define kill criteria upfront:

  • If adoption is below X% after 30 days with marketing support → sunset the feature
  • If the feature hurts a guardrail metric (retention, NPS) → roll back and investigate
  • If the cost of maintaining it exceeds the value it creates → deprecate

Killing features is as important as shipping them. Dead features create maintenance burden, confuse users, and slow your team down.

Key Deliverables

  • Post-launch metrics report (vs targets)
  • User feedback synthesis
  • Launch retrospective document
  • v2 backlog with prioritized improvements
  • Decision: iterate, expand, or sunset

Key principles throughout:

  1. Start with the user problem, not the solution
  2. Validate assumptions before committing resources
  3. Prioritize ruthlessly — say no more than you say yes
  4. Ship small, learn fast, iterate relentlessly
  5. Measure everything, but focus on the metrics that matter
  6. Communicate constantly — no surprises for stakeholders
  7. Every launch is a hypothesis to test, not a destination
